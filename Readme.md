# Matador — Automated FPGA Accelerator Design for Tsetlin Machines

Matador trains Tsetlin Machines and Coalesced Tsetlin Machines and generates RTL. 
This RTL can be deployed on FPGAs (specifically Xilinx SoCs) or simulated using verilator and GTKWave.

## Getting Started

First make sure you have Docker installed and the docker daemon is running. 
You need to make a directory outside of this repo for all your outputs. 
This directory will be mounted in the Docker container. 

```bash
make help         # see all available targets
make build        # build the dev container (one-off)
make shell        # open a shell → dev@matador:/workspace
```
To mount a local data or results directory as `/work` inside the container:

```bash
make shell WORK_DIR=/path/to/your/data
```

GTKWave runs on the **host**, not in the container:

```bash
make waves DIR=path/to/results
```

See `make help` for the full list of targets.

### Build and Verify Setup

```bash
make build                          # build the dev container (one-off)
make tmu-build                      # compile the tmu C extension (one-off)
make shell WORK_DIR=/path/to/data   # enter the container
matador                             # splash screen + guided next step
matador faena                       # interactive toolchain guide
```

## Configuration Files

All Matador commands are driven by YAML files placed in your work directory
(the folder mounted as `/work` inside the container).

### 1. `training_config.yaml` — required for `matador train`

```yaml
# Source: cp examples/training_config.yaml /work/training_config.yaml

tm_type: vanilla          # "vanilla" or "coalesced"
clauses: 400              # total number of clauses (must be even)
classes: 10               # number of output classes
features: 512             # number of Boolean input features per sample
s: 5.0                    # specificity  (float > 1.0)
T: 200                    # voting threshold (integer)
epochs: 50                # training epochs
max_included_literals: 32 # max literals per clause
seed: 42

train_data: /work/data/train.txt   # space-separated Boolean, last col = label
test_data:  /work/data/test.txt
output_dir: /work
```

**Data format:** space-separated, values must already be Boolean (0 or 1).
Last column is the integer class label (0-indexed).

After training, Matador writes:
- `/work/TMIR/<model>.yaml` and `.npz` — the trained model (TMIR format)
- `/work/TMIR/validation_config.yaml` — ready-to-use for `matador validate`
- `/work/TMIR/rom_inference.py` — standalone provenance script (numpy only)

---

### 2. `generate_config.yaml` — required for `matador generate`

One config file drives all backends.  Each backend picks the fields it needs
and ignores the rest.  A backend is only generated if its discriminating
fields are present.

```yaml
# Source: cp examples/generate_config.yaml /work/generate_config.yaml

model_path:      /work/TMIR/<model>.yaml   # from matador train
output_dir:      /work
axis_data_width: 32    # AXI-Stream TDATA width: 32 or 64
fifo_depth:      16    # input FIFO depth (power of 2, ≥ 4)

# ── tiled backend (feat_slice or clause_slice triggers this backend) ──
feat_slice:   8    # features per tile column
clause_slice: 8    # clauses evaluated in parallel per cycle

# ── hardwired backend (pipeline_stages triggers this backend) ──────
pipeline_stages: 3  # adder-tree register stages (0 = combinational)
```

RTL is written to:
- `/work/tiled/RTL/`     — tiled backend
- `/work/hardwired/RTL/` — hardwired backend

To generate only one backend, either omit its discriminating fields or use
`--backend`:
```bash
matador generate --backend tiled     --config /work/generate_config.yaml
matador generate --backend hardwired --config /work/generate_config.yaml
```

---

### 3. `validation_config.yaml` — used by `matador validate`

Auto-generated by `matador train`.  You can also write it manually:

```yaml
model_path: /work/TMIR/<model>.yaml
test_data:  /work/data/test.txt      # optional; enables accuracy reporting
```

---

### Full workflow

```bash
# 1. Train
matador train --config /work/training_config.yaml

# 2. Validate model accuracy (optional)
matador validate --config /work/TMIR/validation_config.yaml

# 3. Generate RTL for all backends
matador generate --config /work/generate_config.yaml

# 4. Emulate (software cycle model, no simulator needed)
matador emulate --backend tiled --config /work/generate_config.yaml --verify

# 5. Simulate RTL testbenches
matador simulate --backend tiled --config /work/generate_config.yaml

# 6. Provenance report (ROM-based inference)
matador provenance \
  --model     /work/TMIR/<model>.npz \
  --test-data /work/data/test.txt
```
